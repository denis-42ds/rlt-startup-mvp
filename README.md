# RLT.Startup MVP

**RLT.Startup** — прототип B2B-маркетплейса, в котором ИИ-агенты координируют взаимодействие покупателей и поставщиков: обрабатывают запросы на коммерческое предложение (RFQ), собирают и сравнивают предложения, помогают согласовывать условия заказа и готовят черновики документов.

## Проблема и ценность

Покупателю нужно отправить запрос нескольким поставщикам, получить сопоставимые условия и выбрать подходящее предложение. Поставщику необходимо быстро обработать запрос, проверить каталог и остатки, рассчитать предложение и согласовать исключения.

RLT.Startup демонстрирует, как разделить эту работу между специализированными агентами и обычными программными сервисами. ИИ автоматизирует интерпретацию запросов и координацию процесса, а детерминированный код проверяет коммерческие ограничения, права доступа и допустимость переходов заказа.

## Что реализовано в MVP

- Извлечение структурированных параметров RFQ из текста с помощью локальной LLM.
- Обработка запросов покупателей и маршрутизация запросов поставщикам.
- Проверка соответствия товаров каталогу, единиц измерения и доступных остатков.
- Подготовка и сравнение предложений поставщиков.
- Создание заказа на основе выбранного предложения.
- Отдельные подтверждения заказа покупателем и поставщиком.
- Проверка допустимости операций и доступности ресурсов на критических этапах процесса.
- Формирование черновиков коммерческого предложения, заказа и отгрузочной спецификации.
- Аутентификация, разграничение доступа и журналирование событий заказов.
- Автоматические тесты бизнес-сценариев, API и контроля доступа.

## Сквозной сценарий

```text
Текст запроса покупателя
          |
          v
Buyer Agent
Извлечение и уточнение параметров RFQ
          |
          v
Orchestrator Agent
Проверка запроса и маршрутизация поставщикам
          |
          +-----------------------+
          |                       |
          v                       v
    Seller Agent A          Seller Agent B
    Каталог и остатки       Каталог и остатки
    Политики поставщика     Политики поставщика
          |                       |
          +-----------+-----------+
                      |
                      v
             Сравнение предложений
                      |
                      v
             Выбор предложения
                      |
                      v
          Подтверждение покупателем
                      |
                      v
          Подтверждение поставщиком
                      |
                      v
                Заказ подтверждён
                      |
                      v
        Три черновика документов
```

Схема отражает логику взаимодействия. Компоненты MVP реализованы в рамках одного приложения, а не как независимо развёрнутые микросервисы.

## Архитектура

### Агентские роли

**Buyer Agent**
- Помогает преобразовать естественно-языковой запрос в структурированный RFQ.
- Выявляет отсутствующие параметры и представляет покупателю сравнение предложений.
- Не подтверждает заказ вместо уполномоченного человека.

**Orchestrator Agent**
- Проверяет запрос и направляет его релевантным поставщикам.
- Собирает, валидирует и нормализует предложения.
- Координирует процесс и обработку исключений.

**Seller Agent**
- Сопоставляет запрос с каталогом и доступными остатками поставщика.
- Проверяет условия и ограничения поставщика.
- Готовит предложение на основании доступных данных.
- Не должен придумывать цены, остатки или самостоятельно менять коммерческие политики.

### Программные сервисы

Контроль доступа, бизнес-политики, переходы состояний, аудит и генерация документов относятся к обычной программной логике. Они не делегируются свободному решению LLM.

Архитектурный стиль — модульный монолит на Python с FastAPI и типизированными контрактами между компонентами.

## Локальная LLM

Для извлечения параметров RFQ интегрирован локальный Ollama API. Модель по умолчанию — `qwen2.5:3b`.

Модель получает текст запроса и формирует структурированные параметры RFQ. Результат проверяется приложением и должен быть просмотрен человеком до подтверждения запроса.

LLM не является источником истины для цены, остатка, полномочий, бизнес-лимитов и переходов состояния заказа. Эти проверки выполняются детерминированным кодом.

Качество извлечения, доля корректных ответов, задержка и потребление памяти пока не оценены на фиксированном тестовом наборе. Известен пример, в котором модель не извлекла место доставки. Поэтому корректность извлечённых параметров нельзя считать гарантированной.

Внешняя LLM не является обязательной зависимостью прототипа и не должна включаться без отдельной оценки качества, стоимости и допустимого состава передаваемых данных.

## Безопасность и доверие

- API использует демонстрационные Bearer-токены для определения субъекта, роли и организации.
- Доступ к операциям и данным проверяется сервером.
- Бизнес-проверки отделены от решений LLM.
- Критические этапы заказа требуют явных подтверждений покупателя и поставщика.
- Перед подтверждениями проверяются полномочия и допустимость операции.
- События заказов журналируются.
- Черновики документов требуют человеческой проверки.
- Демонстрационные секреты должны храниться вне Git и не попадать в логи.

Демонстрационная авторизация не является полноценной системой управления пользователями для публичного развёртывания. Журнал аудита и основные репозитории MVP используют хранение в памяти процесса.

## Проверки качества

Проект использует автоматические проверки для снижения риска регрессий:

- **Ruff** — проверка качества и стиля Python-кода.
- **pytest** — автоматические тесты приложения.
- **GitHub Actions** — запуск проверок при push и создании pull request.

Локальный запуск:

```bash
ruff check .
python -m pytest -q
```

## Технологии

- Python 3.11+
- FastAPI / Uvicorn
- Ollama и локальная LLM `qwen2.5:3b`
- Типизированные модели и контракты
- Pytest для автоматических тестов
- CLI/E2E-сценарий для демонстрации

PostgreSQL рассматривается в целевой архитектуре, но текущая реализация MVP использует in-memory репозитории для RFQ, предложений и заказов. Не следует считать PostgreSQL действующим хранилищем этой версии без отдельной проверки кода и конфигурации.

## Запуск в Debian/Linux

### 1. Подготовка окружения

Из корня репозитория:

```bash
source .venv/bin/activate
```

Если окружение ещё не создано, создайте его в соответствии с используемым в проекте способом. Установка проекта в editable-режиме:

```bash
python -m pip install -e .
```

Перед первым запуском убедитесь, что локальная LLM доступна через Ollama и модель `qwen2.5:3b` подготовлена в соответствии с конфигурацией проекта.

### 2. Локальная конфигурация

Для демонстрации используются:

- `RLT_DEMO_BUYER_TOKEN`
- `RLT_DEMO_SUPPLIER_TOKEN`
- `RLT_DEMO_ORCHESTRATOR_TOKEN`
- `RLT_DEMO_CREDENTIALS` — объединённая конфигурация демонстрационных учётных данных.

Локальная конфигурация хранится в `.env.demo`. Загружайте её в каждом терминале, где запускается приложение или выполняются тесты:

```bash
source .env.demo
```

Убедитесь, что процесс получает необходимые переменные окружения. Если конфигурация не загружена, сценарий демонстрации может сообщить об отсутствующем токене.

**Не публикуйте содержимое `.env.demo`, токены или другие секреты. Не добавляйте этот файл в Git.**

### 3. Запуск API

В первом терминале:

```bash
source .venv/bin/activate
source .env.demo
uvicorn rlt_startup.demo_api:app --host 127.0.0.1 --port 8000
```

API запускается на `http://127.0.0.1:8000` и доступен локально.

### 4. Полная сквозная демонстрация

Во втором терминале:

```bash
source .venv/bin/activate
source .env.demo
python scripts/e2e_demo.py
```

Успешный сценарий завершается сообщением:

```text
E2E PASS: весь сценарий завершился успешно.
```

Сценарий демонстрирует обработку RFQ, предложения нескольких поставщиков, сравнение, оформление заказа, подтверждения сторон и формирование трёх черновиков документов.

### 5. Интерактивная демонстрация локальной LLM

При работающем API:

```bash
source .venv/bin/activate
source .env.demo
python scripts/e2e_demo.py --interactive
```

Введите запрос на поставку обычным языком, проверьте извлечённые параметры и подтвердите RFQ после ручной проверки.

Интерактивный режим полезен для показа локального извлечения параметров и сравнения предложений. Он не выполняет весь путь оформления заказа, доступный в полном E2E-сценарии.

### 6. Автоматические тесты

В отдельном терминале:

```bash
source .venv/bin/activate
source .env.demo
pytest -q
```

Последний предоставленный результат:

```text
169 passed in 0.95s
```

Также был предоставлен результат успешного полного E2E-сценария. Результаты относятся к запуску разработчика в его окружении.

### 7. Команды Makefile

Для упрощения локального запуска, тестирования и остановки API в проекте предусмотрен `Makefile`. Команды выполняются из корня репозитория.

Перед использованием убедитесь, что виртуальное окружение `.venv` создано, зависимости установлены, а файл `.env.demo` настроен.

#### Запуск и остановка API

Запустить API в фоновом режиме:

```bash
make up
```

Команда запускает Uvicorn на `http://127.0.0.1:8000`, сохраняет PID процесса в `.run/api.pid` и вывод запуска в `.run/api.log`. После запуска выполняется проверка доступности `/health`.

Остановить API:

```bash
make down
```

Команда отправляет процессу API сигнал завершения и ожидает его остановки.

#### Проверка состояния и просмотр логов

Проверить доступность API:

```bash
make health
```

При успешном ответе API возвращает статус `ok`. Если API недоступен, команда завершается с ошибкой.

Показать последние 30 строк лога:

```bash
make logs
```

Непрерывно следить за логом:

```bash
make logs-follow
```

Для завершения просмотра нажмите `Ctrl+C`. Это прекращает просмотр лога, но не останавливает API.

#### Тестирование и E2E-сценарии

Запустить автоматические тесты:

```bash
make test
```

Выполнить полный сквозной сценарий:

```bash
make e2e
```

Запустить интерактивную демонстрацию локальной LLM при работающем API:

```bash
make interactive
```

Интерактивный режим позволяет ввести запрос покупателя обычным языком и проверить извлечение параметров RFQ. Как и при прямом запуске скрипта, результат зависит от доступности и корректной настройки локальной LLM.

Команды тестирования используют виртуальное окружение проекта и загружают переменные из `.env.demo` в соответствии с настройками Makefile.

#### Типовой цикл работы

```bash
make up
make health
make e2e
make test
make logs
make down
```

Если API не запускается или проверка `/health` завершается ошибкой, изучите вывод `make up` и последние записи через `make logs`.

Каталог `.run/` содержит локальные служебные файлы запуска и логи. Его содержимое не предназначено для хранения в Git.

## Ограничения MVP

- RFQ, предложения и заказы хранятся в памяти процесса и не восстанавливаются после перезапуска.
- Аудит заказов также использует in-memory хранилище и не обеспечивает долговременное хранение.
- Остатки проверяются, но атомарного резервирования товара нет.
- Автоматическое преобразование единиц измерения не поддерживается.
- Локальная LLM может пропускать или неверно извлекать поля; требуется проверка человеком.
- Качество и производительность LLM пока не оценены систематически.
- Документы формируются как черновики. Подписание, электронная подпись и ЭДО не входят в текущий объём.
- Интерфейс текущего прототипа — API и CLI-сценарии, а не готовый пользовательский веб-интерфейс.
- Перед публичным развёртыванием необходимы дополнительная проверка безопасности и анализ требований к персональным и коммерчески чувствительным данным.

## Направления развития

1. Постоянное хранение RFQ, предложений, заказов и событий аудита.
2. Воспроизводимая оценка локальной LLM на фиксированном наборе RFQ.
3. Дополнительные тесты политик, эскалаций и недопустимых переходов.
4. Атомарное резервирование остатков.
5. Пользовательский интерфейс покупателя и поставщика.
6. Интеграции с реальными каталогами и ERP после подтверждения потребности.

## Статус

MVP демонстрирует основной путь B2B-сделки между покупателем и поставщиками с координацией специализированных ИИ-агентов, проверками бизнес-правил и контролем критических действий человеком.

Текущая версия предназначена для демонстрации и проверки концепции, а не для непосредственного использования в производственном коммерческом процессе.
